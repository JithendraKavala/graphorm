# ADR-0003: JDBC-Based Execution Engine

**Date:** 2024-11-01
**Status:** Accepted
**Deciders:** GraphORM maintainers

---

## Context

GraphORM needs a database access layer. The main options for Java are: JPA/Hibernate, Spring Data, jOOQ, JDBI, plain JDBC, or R2DBC (reactive).

GraphORM's goal is to be a framework that generates and executes SQL based on its own schema model. Using JPA or Hibernate would introduce a competing ORM layer with its own entity model, caching behavior, and query generation that would conflict with GraphORM's own query planning.

## Decision

GraphORM uses plain JDBC (via `java.sql`) with HikariCP for connection pooling. No ORM framework (JPA, Hibernate, MyBatis) is used in the core execution path.

SQL is generated by GraphORM's own query engine and executed via `PreparedStatement`. Results are mapped via `ResultSet` by GraphORM's own result mappers.

HikariCP is the connection pool. It is the industry standard, battle-tested, and the same pool used by Spring Boot by default.

## Alternatives Considered

| Alternative | Why Rejected |
|-------------|-------------|
| JPA / Hibernate | Competing ORM — introduces entity model conflicts, caching complexity, and query generation that would need to be bypassed entirely |
| Spring Data JDBC | Requires Spring as a core dependency; GraphORM core must be Spring-agnostic |
| jOOQ | External SQL DSL — GraphORM generates its own SQL DSL from its schema model; jOOQ would be a redundant dependency |
| JDBI | Useful but adds an abstraction layer GraphORM does not need |
| R2DBC (reactive) | Reactive I/O complicates the execution model; not aligned with blocking Spring MVC patterns used in typical Spring Boot apps |

## Consequences

**Positive:**
- Complete control over SQL generation, binding, and result mapping
- No ORM magic — behavior is explicit and testable
- No competing entity model or caching layer
- Lightweight — only JDBC + HikariCP as runtime dependencies in the JDBC module
- GraphORM core is not forced to depend on Spring

**Negative / Trade-offs:**
- More manual work than a higher-level abstraction
- Result mapping must be explicitly implemented for every type
- No query cache or identity map (by design — these would add complexity without clear benefit at this stage)

## Compliance

- `graphorm-core` must not import any JDBC classes
- `graphorm-jdbc` owns all JDBC interactions
- `PreparedStatement` with `?` parameters must be used exclusively — string SQL concatenation is prohibited
