# M3 — PostgreSQL JDBC Layer

**Status:** ⚪ Not Started
**Depends on:** M1

---

## Objective

Establish reliable, safe database execution against real PostgreSQL. This milestone provides the JDBC execution infrastructure that all higher-level query operations depend on.

---

## Scope

### Connection Management
- HikariCP `DataSource` configuration and integration
- Connection acquisition and release
- Pool sizing and timeout configuration via properties

### Prepared Statement Execution
- `PreparedStatementExecutor` — bind parameters, execute, handle results
- Support for `java.sql.Types` including: `VARCHAR`, `INTEGER`, `BIGINT`, `BOOLEAN`, `TIMESTAMP`, `NUMERIC`, `UUID`, `OTHER` (JSONB)
- Batch execution (`PreparedStatement.addBatch()`)

### Result Mapping
- `ResultSetMapper<T>` — maps a `ResultSet` row to a Java object
- Type conversion for all supported scalar types
- Null handling (distinguish SQL NULL from Java null explicitly)
- Generated key retrieval (`RETURN_GENERATED_KEYS`)

### Transaction Management
- `TransactionContext` — holds a connection and tracks transaction state
- `begin()`, `commit()`, `rollback()`, `savepoint(String)`, `releaseSavepoint()`
- `TransactionManager` — manages transaction lifecycle
- Connection is not returned to pool until transaction completes

### SQL Execution Abstractions
- `JdbcExecutor` — the main entry point for executing SQL against a `DataSource`
- Methods: `query(sql, params, mapper)`, `update(sql, params)`, `batchUpdate(sql, paramsList)`, `queryForObject(sql, params, mapper)`, `queryWithGeneratedKey(sql, params, keyMapper)`

---

## Expected Deliverables

1. `JdbcExecutor` can execute parameterized SELECT, INSERT, UPDATE, DELETE against PostgreSQL
2. Transactions commit and roll back correctly
3. All connections are released to the pool after each operation (no leaks)
4. Generated primary keys are correctly returned and mapped
5. All type conversions handle null correctly

---

## Acceptance Criteria

- [ ] Integration tests pass against PostgreSQL 16 via Testcontainers
- [ ] SQL parameters are always bound via `PreparedStatement` — no string concatenation exists
- [ ] A connection acquired for a query is released back to the pool in all paths (success, exception)
- [ ] `rollback()` after a failed INSERT leaves the row absent from the database (verified by integration test)
- [ ] Generated IDs from `INSERT ... RETURNING id` are correctly mapped to the Java return type
