# M9 — Transactions, Concurrency and Reliability

**Status:** ⚪ Not Started
**Depends on:** M7

---

## Objective

Ensure correctness under concurrent real-world workloads. After M9, GraphORM handles multi-user scenarios, concurrent updates, deadlocks, and complex transaction patterns reliably.

---

## Scope

### Isolation Levels
- `READ_COMMITTED` (PostgreSQL default)
- `REPEATABLE_READ`
- `SERIALIZABLE`
- Configuration per-operation and per-transaction block

### Row-Level Locking
- `SELECT ... FOR UPDATE` — exclusive row lock
- `SELECT ... FOR SHARE` — shared row lock
- `NOWAIT` and `SKIP LOCKED` options (for queue-style processing)

### Optimistic Concurrency
- Version field (`@version`) detection in schema
- On update: `WHERE id = ? AND version = ?`; fail if no rows updated (`OptimisticLockException`)
- Increment version on successful update

### Savepoints
- `SAVEPOINT <name>` within a transaction
- `ROLLBACK TO SAVEPOINT <name>`
- `RELEASE SAVEPOINT <name>`

### Transaction Propagation (Spring Integration)
- Participation in Spring's `@Transactional` when Spring is on the classpath
- `TransactionManager` integrates with Spring's `PlatformTransactionManager`

### Bulk Operations
- `createMany` with conflict handling
- `updateMany` with filter-driven bulk update
- `deleteMany` with safe filter requirements

### Deadlock and Failure Handling
- PostgreSQL deadlock detection (error code `40P01`) caught and translated to `DeadlockDetectedException`
- Retry hints documented (not built-in retry — consuming application decides retry policy)
- Connection errors during transaction translated with consistent exception types

### Idempotency Patterns
- UPSERT (from M8) as an idempotency tool
- `IF NOT EXISTS` patterns
- Idempotency key support via `@idempotencyKey` field (optional)

### Concurrent Update Testing
- Concurrent inventory reservation scenario
- Multiple threads attempting to decrement the same stock count
- Correct serialization verified

## Acceptance Criteria

- [ ] 10 concurrent threads decrementing inventory by 1 each result in exactly a final value of `initial - 10` (no double-spend, no lost update), verified by integration test
- [ ] `SERIALIZABLE` isolation prevents phantom reads in a concurrent scenario (tested with Testcontainers)
- [ ] `OptimisticLockException` is thrown when an update targets a row whose version has changed since it was read
- [ ] Rollback after a constraint violation restores data consistency (no partial writes)
- [ ] A deadlock is detected and translated to `DeadlockDetectedException` (not an opaque `DataAccessException`)
- [ ] Savepoints allow partial rollback within a transaction
